## Versioning and Changelog

For every change beyond a minor fix (typo, comment, formatting), update both files below in the same commit/PR:

1. **`package.json`** - Bump the `version` field using semantic versioning (`MAJOR.MINOR.PATCH`):

   - **Major (X.0.0):** Breaking changes, incompatible API changes, or removal of existing functionality.
   - **Minor (0.X.0):** New features or moderate changes that are backward-compatible.
   - **Patch (0.0.X):** Bug fixes, small tweaks, or internal changes with no user-facing behavior change.
   - Each number resets the ones to its right on bump (e.g. minor bump: `2.0.18` -> `2.1.0`; major bump: `2.1.5` -> `3.0.0`; patch bump: `2.0.18` -> `2.0.19`).
2. **`CHANGELOG.md`** - Add a new heading for the version, following [Keep a Changelog](https://keepachangelog.com/) format:

   - Place the newest version at the top, directly below the `# Changelog` title.
   - Use the format: `## [X.Y.Z] - YYYY-MM-DD`
   - Group entries under `Added`, `Changed`, `Fixed`, or `Removed` as applicable.
   - Write concise, single-line bullet points. No duplicate or near-duplicate entries; if a later change supersedes an earlier unreleased entry, edit the original instead of adding a new line.
   - Do not log purely internal changes (refactors, comment updates) unless they affect behavior or the public API.

Skip this process only for changes that touch no functionality: comments, formatting, whitespace, or internal documentation.

Whenever a change alters user-visible behavior, supported providers/services, settings, IPC channels, config keys, architecture or commands, update every doc that mentions it in the same commit/PR, not just the changelog. Search the repo for the old name or behavior (e.g. `rg -i "sarvam|assemblyai"`) to find stale references. Check these places:

- `site/index.html` (meta tags, JSON-LD, hero, feature cards, comparison table, FAQ, CTA).

Keep wording consistent across all of them, and do not leave references to removed files, channels or keys.

## Codebase Architecture

Three artifacts build from this one repo: the Electron desktop app (Windows, and macOS 14.2+ as a beta), its React renderer, and an optional Chrome MV3 extension (`extension/`) that bridges Google Meet/Zoom to the desktop app. The desktop app also detects meetings natively on Windows, so the extension is slated for removal.

- **Main process** (`electron/main.js`) owns the window/tray, all `ipcMain` handlers, the recording state machine, and `runProcessingPipeline()` (transcribe → generate notes → optional Notion upload). `electron/preload.js` exposes this surface to the renderer as `window.meetmind.*` (contextIsolation on, nodeIntegration off) — grouped by feature: `window`, `recording`, `sessions`, `notion`, `gemini` (default prompts), `providers` (descriptor list + generic connection test), `processing`, `capture`, `permissions` (macOS), `updater`, `ffmpeg` — plus `platform` (`process.platform`; the renderer reads it through `renderer/lib/os.js`).
- **Platforms**: OS-specific code is gated on `process.platform` (`isMac` in main, `isMac`/`isWindows` from `renderer/lib/os.js`). macOS gets a native-traffic-light window (`titleBarStyle: 'hiddenInset'`; the renderer hides its own window buttons), an app menu, a template tray icon, `open-url` deep links registered before `ready`, and a non-activating `panel` overlay. macOS builds are ad-hoc signed (no Apple Developer ID yet), so `electron/services/updater.js` only checks for updates there (`canSelfUpdate`) and opens the release page, and macOS forgets privacy permissions after each update. `electron/services/permissions.js` reads/requests microphone and Screen & System Audio Recording access (`permissions:*` IPC) for the Settings › System Permissions card.
- **Audio capture** has two paths: the primary path has the renderer capture system audio via Electron's display-media loopback + mic via Web Audio, streaming chunks to main over `capture:chunk` IPC which appends them to an in-progress `.webm` on disk; on stop, `convertWebmToWav()` (`electron/audio/recorder.js`, ffmpeg-backed) produces the final `.wav`. Loopback is WASAPI on Windows and the CoreAudio Tap API on macOS 14.2+ (needs `NSAudioCaptureUsageDescription`); on macOS the video source getDisplayMedia requires is set by `config.macCaptureStrategy` (`screen`/`frame`/`picker`, `electron/audio/mac-capture.js`), which Settings › System › Test system audio tries one by one (`capture:test-begin`/`capture:test-end`). If renderer capture fails to start, `handleStartRecording()` falls back on Windows to direct ffmpeg dshow capture (mic + Stereo Mix); macOS has no fallback, and the renderer records the mic alone when it gets no system audio.
- **Providers** (`electron/providers/`): every STT and LLM engine is a self-describing module (`stt/*.js`, `llm/*.js`) registered in `providers/index.js`. A provider declares its metadata (credentials, curated models, default model, guide, capabilities) plus `transcribe()`/`generate()` and `test()`. The renderer's Settings, key checks and connection tests are generated from the descriptors served by `providers:list`/`providers:test`, and config keys are derived from them; adding an engine means one new file, one registry line and an icon (see `docs/ADDING_PROVIDERS.md`). Provider modules must not import `electron` at load time so they stay unit-testable.
- **Processing pipeline** (`runProcessingPipeline` in `main.js`): Stage 1 transcription (`electron/services/transcription.js`, a thin controller that checks for silence and dispatches to the provider in `config.sttService` with its model from `config.sttModels`) — Google STT v1/v2, AssemblyAI, Sarvam AI (`saaras:v3`, needed for English/Indic code-switching) or Groq Whisper. Stage 2 (`electron/services/notes.js`) builds the prompt for `noteOutputMode`, calls the LLM in `config.llmProvider` (Gemini, Groq or Claude, model from `config.llmModels`), and retries once with `config.llmFallback` (any provider/model) if it fails. Every LLM provider streams (`generate()`'s `onText`), and the notes written so far go to the renderer as `notes:preview` for a live preview on the meeting page (`buildNotesPreview` in `notes-normalize.js`: `partial-json` for JSON mode; the renderer runs Markdown through `remend`). Stage 3 (`electron/services/notion.js`) is optional and only runs if a Notion token + page ID are configured. Progress is pushed to the renderer (`processing:progress`) and to the extension (WS broadcast) at each stage, and during notes generation it climbs from 60% to 84% with an estimate of how much of the notes is written (`estimateNotesProgress`).
- **Persistence**: `electron/db/sessions.js` uses `sql.js` (SQLite compiled to WASM) held in memory and rewritten to a single file on every mutation — there's no migration system, schema is `CREATE TABLE IF NOT EXISTS`. `electron/utils/config.js` wraps `electron-store` for settings/API keys.
- **Meeting detection + overlay** (Windows only for now; `detection/win32.js` reports unavailable elsewhere and the Settings switch is hidden on macOS): `electron/detection/meeting-detector.js` polls every 1.5 s which apps hold the mic (active WASAPI capture sessions via COM, merged with the `CapabilityAccessManager\ConsentStore\microphone` registry's `LastUsedTimeStop == 0`, which some Windows installs stop updating) and the visible window titles, both read through `koffi` FFI in `detection/win32.js` (loaded lazily). The pure rules and debounce/end/dismiss state machine live in `detection/meeting-rules.js` and are unit-tested. A browser counts only with a Meet/Zoom/Teams tab title seen in the last 2 min; the Zoom/Teams desktop apps count on mic use alone. `main.js` keeps one `overlayState` (prompt → recording → ended → processing → complete/error), fed by `broadcastStatus()` next to every extension broadcast, and `electron/overlay/overlay-window.js` shows it in a frameless, transparent, always-on-top, non-focusable window rendering `renderer/overlay.html` with its own sandboxed preload (`electron/overlay-preload.js`, `window.meetmindOverlay`). It never stops a recording on its own: when the meeting ends it asks. Gated by the `meetingDetection` config key.
- **Desktop ↔ extension bridge**: `electron/websocket-server.js` runs a local WS server, scanning ports 39842–39852 until one is free, and only accepts connections with a `chrome-extension://` origin. The extension's service worker (`extension/background.js`) probes the same port range, sends `START_RECORDING`/`STOP_RECORDING`/`APP_STATUS`, and relays `RECORDING_STARTED`/`PROCESSING_PROGRESS`/`PROCESSING_COMPLETE` broadcasts to the floating overlay injected into Meet/Zoom tabs by `extension/content.js` + `extension/overlay/`.
- **PDF export**: the renderer builds a self-contained HTML document (`renderer/components/note/pdfDocument.jsx`, loaded on demand; same react-markdown + remark-gfm rendering as the notes view), and `pdf:export` in `main.js` prints it via a hidden sandboxed window in `electron/services/pdf-export.js` to `config.pdfExportDir` (Downloads when empty) as `YYYY-MM-DD-HHmm-Title.pdf`, never overwriting.
- **Renderer** (`renderer/app.jsx`): no router, just view-state switching between `Dashboard.jsx` (session list), `NoteViewer.jsx`/`TranscriptViewer.jsx` (a completed session), `Settings.jsx` (API keys, service selection, FFmpeg install flow, onboarding), and `LogsViewer.jsx` (tails `electron/utils/logger.js` output via the `log:entry` IPC event).
- **Build/package**: Vite builds the renderer into `dist/renderer/` from two entries (`index.html` and the meeting overlay's `overlay.html`); `scripts/build-extension.js` zips `extension/` into `dist/meetmind-extension.zip`; `electron-builder.yml` packages the Windows NSIS installer and the macOS DMGs + update zips (arm64 and x64, ad-hoc signed, `minimumSystemVersion` 14.2, entitlements in `assets/entitlements.mac.plist`), pulling ffmpeg in as `extraResources` per platform (never bundled in the asar): Windows from `assets/ffmpeg/*.exe`, macOS from `assets/ffmpeg/mac-<arch>/`, filled by `scripts/fetch-ffmpeg.js` from the SHA-256 pins in `electron/audio/ffmpeg-sources.js`, the single list of every FFmpeg build MeetMind ships or installs (unpacked by `electron/audio/ffmpeg-fetch.js`). There is no `electronVersion` pin: electron-builder packages the Electron the lockfile installed. `electron/audio/ffmpeg-path.js` resolves the binaries (bundled → macOS `userData/ffmpeg` → Homebrew → PATH). Without them, the `ffmpeg:install` IPC handler (`electron/services/ffmpeg-installer.js`) installs the same pinned, checksum-verified build: next to the bundled copy on Windows, into `userData/ffmpeg` on macOS. `electron/smoke.js` (`MeetMind --smoke`) is a headless self-test of a packaged app (config, DB, FFmpeg, WebM→WAV, koffi, permissions, detection) that CI runs on both platforms.

## Commands

Run `pnpm run lint` and `pnpm run test` before finishing a change. The tests cover pure logic only (note Markdown export/parse, formatting, PDF file naming, waveform peaks, meeting filters/sort, meeting search, meeting-detection rules, meeting titles, launch at login, Settings save diffs, FFmpeg path resolution and pins, macOS capture-test verdicts) plus a server-rendered check of the macOS Permissions card, so also verify UI and main-process changes by running the app (`pnpm run dev`) and exercising the affected flow directly. There is no maintainer Mac: macOS changes are verified by the `mac-build` CI job (build, `codesign --verify`, `--smoke`; its zipped `.app` artifact is what testers run) and by testers on real hardware.

The package manager is pnpm (pinned via `packageManager` in `package.json`); never use npm/npx or commit a `package-lock.json`. `pnpm-workspace.yaml` sets `nodeLinker: hoisted` so electron-builder sees a flat `node_modules`, `supportedArchitectures` (both CPUs) so one Mac can package arm64 and x64, and lists the dependencies allowed to run install scripts under `allowBuilds` (add new ones with `pnpm approve-builds <pkg>`). `verifyDepsBeforeRun: warn` stops `pnpm run` from silently reinstalling after `package.json` changes, because that reinstall replaces `node_modules/electron` and breaks it if the app is running; run `pnpm install` explicitly with the app closed. Electron (42+) has no install script: it downloads its binary on first launch, and if it reports it "failed to install correctly", run `pnpm exec install-electron`. `minimumReleaseAge: 1440` makes pnpm refuse package versions published less than a day ago, a supply-chain guard; Dependabot has its own 7-day `cooldown` in `.github/dependabot.yml`. If `pnpm add`/`pnpm update` says a version is too new, wait, or for an urgent security fix add the package to `minimumReleaseAgeExclude` temporarily. Never remove the setting.

- `pnpm install` — install dependencies (Node 22.12+, Windows or macOS)
- `pnpm run lint` — ESLint (flat config in `eslint.config.mjs`) over `electron/`, `renderer/`, `extension/`, `scripts/` and `tests/`
- `pnpm run test` — Vitest suite in `tests/` (`vitest.config.mjs`, Node environment); `pnpm run test:watch` for watch mode. Tests live in `tests/`, not next to the code, so electron-builder never packages them
- `pnpm run dev` — full dev loop: regenerates icons + rebuilds the Chrome extension (`predev`), then runs Vite and Electron concurrently. Renderer serves at http://localhost:5173; Electron opens DevTools automatically in dev
- `pnpm run dev:renderer` — Vite dev server only
- `pnpm run dev:electron` — Electron only (expects `dev:renderer` already running on :5173)
- `pnpm run build:ext` — rebuild just `dist/meetmind-extension.zip` from `extension/` via `scripts/build-extension.js`
- `pnpm run build:dir` — production renderer build + unpacked Electron app under `dist/desktop/` (fast iteration, skips installer packaging)
- `pnpm run build` — full production build: Vite build + electron-builder NSIS installer (`dist/desktop/MeetMind-Setup-X.Y.Z.exe`). Requires `assets/ffmpeg/ffmpeg.exe` and `assets/ffmpeg/ffprobe.exe` to already exist (not committed — `pnpm run fetch-ffmpeg`)
- `pnpm run fetch-ffmpeg` — download the pinned FFmpeg for this OS, verifying each SHA-256: `assets/ffmpeg/*.exe` on Windows, `assets/ffmpeg/mac-arm64/` and `mac-x64/` on macOS (`-- --arch arm64` for one; `-- --platform win32|darwin` to fetch another OS's)
- `pnpm run build:mac` — on a Mac: both DMGs + update zips + `latest-mac.yml` (`dist/desktop/MeetMind-X.Y.Z-{arm64,x64}.dmg`), ad-hoc signed; needs `fetch-ffmpeg` first. `pnpm run build:mac:dir` builds just the unpacked app for the host arch
- `<packaged app> --smoke` — headless self-test (`electron/smoke.js`); prints `MEETMIND_SMOKE {json}` and exits non-zero on failure. Also works in dev: `node_modules/electron/dist/electron . --smoke`. Run it from bash, not PowerShell (which doesn't wait for a GUI app's output); `node scripts/check-smoke.js <output file>` checks the result, as CI does
- `pnpm run generate-icons` — regenerate `assets/icons/*` from the source icons, including the 1024px `icon.png` the macOS `.icns` comes from and the macOS menu-bar `trayTemplate*.png`

## CI/CD

All workflows are in `.github/workflows/` and share `.github/actions/setup` (pnpm from `packageManager`, Node 24, `pnpm install --frozen-lockfile`).

- **`ci.yml`** runs on every PR and push to `main`; a new commit on a PR cancels its run still in progress, and a push to `main` whose files are identical to a merged PR commit that already passed CI skips every job but the dependency audit (`already-tested`, which reads the API only; release gates never skip: `release.yml` passes `always-run: true`). A called workflow can't ask for more permissions than its caller grants, or the caller fails to start (`startup_failure`), so `release.yml`'s `checks` job must grant every permission a `ci.yml` job requests (today `actions: read` and `pull-requests: read` for `already-tested`). It lints, tests, and builds the renderer and extension; packages the unpacked Windows app (`windows-build`) and the unsigned Apple Silicon app (`mac-build`, which also checks the signature and Info.plist privacy keys and uploads the zipped `.app` for testers), each running the pure-logic tests and `--smoke` (results in the job summary via `scripts/check-smoke.js`); a `changes` job skips those two builds on PRs that only touch docs; runs repo hygiene checks (no npm/yarn lockfile, `.exe`/`.dll`/`.dylib` or anything in `assets/ffmpeg/` but its README, real `.env` file, or file over 10 MB); scans the full git history for API keys with gitleaks (checksum-verified download); runs `pnpm audit --prod --audit-level high`; and audits the workflows themselves with zizmor. It's also a reusable workflow.
- **`release.yml`** calls `ci.yml` as a required gate. The `build` job (Windows) then builds the installer with a read-only token and no dependency cache, bundling the pinned, checksum-verified FFmpeg (`scripts/fetch-ffmpeg.js`); the `build-mac` job (`macos-latest`, same rules) fetches the pinned macOS FFmpeg for both arches, runs `pnpm run build:mac`, verifies both apps and that `latest-mac.yml` lists both update zips. Both smoke-test their packaged app. An `attest` job, which runs no project code and is the only one with `id-token`/`attestations: write`, signs SLSA build provenance for every downloadable file (`gh attestation verify <file> --repo aslahtp/meetmind`); then a separate `publish` job, the only one with `contents: write`, runs no dependency code or third-party actions, and creates the release with the runner's `gh` CLI. `pnpm run build` passes `--publish never`, so electron-builder never needs a token.
- **`pr-checks.yml`** runs on PRs only. The version-and-changelog check fails any PR that changes code without bumping `package.json` and adding a matching `## [X.Y.Z] - YYYY-MM-DD` heading; docs and `.github/` changes are exempt, and a `skip-version-check` label overrides it. Dependency review fails a PR that adds a runtime dependency with a high-severity advisory.
- **`codeql.yml`** runs CodeQL security analysis of the JavaScript and of the workflows themselves (`actions` language) on PRs, pushes, and weekly. **`.github/dependabot.yml`** opens grouped weekly minor/patch dependency PRs and monthly action updates (workflows and the composite setup action), each with a 7-day cooldown. Every job has a `timeout-minutes`. **`.github/CODEOWNERS`** requires maintainer review for workflow, dependency, build and updater files.

This is a public repo that takes PRs from forks, so treat workflow changes as security changes:

- Pin every third-party action to a full 40-character commit SHA with a `# vX.Y.Z` comment (Dependabot updates both). Never use a tag or branch. Reference this repo's own actions and reusable workflows with the self-repository syntax `uses: $/.github/...`, not `./`; it resolves to the running commit and can't be swapped out by files changed during the run. actionlint 1.7.12 doesn't recognise `$/` yet, so ignore that error.
- Trigger on `pull_request`, never `pull_request_target` or `workflow_run` running PR code. Fork PRs then get a read-only token and no secrets.
- Keep `permissions: contents: read` at the top of every workflow and grant more only per job, with a comment saying why. Set `persist-credentials: false` on every checkout.
- Never interpolate `${{ }}` expressions from event data (PR titles, branch names, labels) into `run:` scripts; pass them through `env:` instead.
- Checksum-verify any binary a workflow downloads.
- Run zizmor locally before pushing workflow changes (`pip install zizmor`, then `zizmor .`); CI fails on its findings.

If `pnpm audit` fails, try `pnpm audit --fix update` first. It re-resolves the lockfile to patched versions inside the existing ranges, without adding overrides.

## Learned Workspace Facts

- MeetMind renderer uses React + Tailwind; theming is driven by CSS variables in `renderer/styles/globals.css` and Tailwind `darkMode: 'class'` with `<html class="dark">` in `renderer/index.html`.
- Prefer using CSS variables (`--color-*`) with Tailwind arbitrary values like `bg-[rgb(var(--color-background))]` instead of hardcoded hex colors for consistent theming.
- Electron packaging must include `dist/renderer/**` in `package.json` `build.files`; otherwise the installed app can open a blank window because `dist` is gitignored.
- Prevent duplicate running instances/tray icons by using `app.requestSingleInstanceLock()` in `electron/main.js` and focusing the existing window on `second-instance`.
- Don’t commit bundled FFmpeg `.exe` binaries over GitHub’s 100MB limit; keep them ignored or manage them via Git LFS / external download.
- Meetings commonly mix English with Indic languages, so transcription and language models should support code-switching between them.
